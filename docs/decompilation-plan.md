# Static decompilation plan (Ghidra)

This plans the roadmap's still-open item: *"Analyze the full v1.01 EXE statically, starting from DAT/SAV I/O, end-turn, city changes, movement, combat, diplomacy, AI, and victory messages"* (`roadmap.md` §3). It exists because several mechanics cannot be recovered from save-file diffing at all — combat resolution, AI decisions, and exact cost/income formulas are computed at runtime and never fully serialized. Tooling: Ghidra 12.1.3 + Temurin JDK 21, installed locally under `%LOCALAPPDATA%\ReTools`, kept outside this repository like the game assets. **The executable is not run** — this is static analysis of the same read-only file already hashed in `impconq2-sha256.txt`, consistent with every prior report and the roadmap's explicit constraint that running the original binary is a separate, not-yet-authorized step.

## Why this is tractable

The binary is Delphi (Delphi 2 era), which embeds method-name tables and form resources far more legible than a typical stripped C/C++ build — already proven useful without a decompiler in `battle-code-entry-points.md` (found `TBattleMap.StartBattle`, `MoveHumanUnit`, `EndTurn`, `ComputerGeneral`, `Surrender`, `FinishBattle` and code-to-string cross-references purely from RTTI, before Ghidra was ever installed) and `menu-and-toolbar-inventory.md` (found event handlers `StrategicDecision`, `ChangeNation`, `ShowOnAreaMap`, `UnitMapAction` and the `TMainMenu` stream). Ghidra's headless mode can auto-analyze and export decompiled pseudocode without any GUI interaction, so this is fully drivable end-to-end.

## Setup status: working, with one gap found

Ghidra 12.1.3 + Temurin JDK 21 are installed under `%LOCALAPPDATA%\ReTools` (outside this repo). Headless import and auto-analysis of the full v1.01 EXE succeeds cleanly in about 30 seconds. Decompiling by address works and produces genuine, readable pseudocode — verified by decompiling the seven known `TBattleMap` addresses from `battle-code-entry-points.md`; `StartBattle` (`0x00436fb4`) contains the literal constant `0x1c0` (448), matching the tactical grid's known 14-tile width at 32 px/tile from `battle-observation.md`.

**Gap:** Ghidra's own analyzer does not recover Delphi's RTTI method-name tables automatically — every function comes back auto-named `FUN_xxxxxxxx` unless targeted by an address already known from prior manual byte-level reading (as `battle-code-entry-points.md` and `menu-and-toolbar-inventory.md` did without any decompiler at all). This means:

- [x] **0. Recover Delphi RTTI symbols in Ghidra.** Done: a Python scanner recovered the exact method-table byte format (`Word Count` + entries of `{Word EntrySize; Pointer Addr; Byte NameLen; Name}`, followed by the class name in the same format) by matching it byte-for-byte against the seven known `TBattleMap` addresses, then applied it across the whole 1,166,336-byte EXE. Result: **282 methods across 31 classes**, every one matching a real class name (all 30 `TPF0` forms plus `TObject`), imported into Ghidra as real symbols (`ClassName_MethodName`). This is what made the priority queue below tractable immediately instead of needing a hand-found address per target. See [decompiled-fleet-tax-and-mercenary-formulas.md](reports/decompiled-fleet-tax-and-mercenary-formulas.md).

**A second gap found:** Ghidra's `ReferenceManager`/`getReferencesTo()` does not find code references to several known-real string literals in this binary (tested on the DAT filename and `"falls to"` — both zero results, and a raw byte scan for the address as an immediate operand also found nothing). The earlier successful `SHOOTS AT`/`ATTACKS` lookups worked only because those *addresses* were already known from prior manual work; `getFunctionContaining()` doesn't need Ghidra's reference index, only `getReferencesTo()` does, and that's what's failing here. **A third, smaller gap:** `analyzeHeadless.bat` takes the *parent* directory plus the project name (`... \ReTools\ghidra_projects IC2`), not the `.rep` directory; passing `ghidra_projects\IC2` fails with "Could not find project". Also, `DumpListing.java` silently emits an empty body for a function Ghidra knows only as an imported symbol (e.g. `TUnitMap_JoinArmies`, `TUnitMap_SplitArmy`), even though the decompiler handles it — so an assembly-level sweep must be cross-checked against the decompiled dump rather than trusted alone. **Workaround that works:** decompile every function in the application's address range to one text file (`ExportAllInRange.java`, ~1,900 functions took a few minutes) and grep the *decompiled output* for the string — Ghidra's decompiler inlines string-literal operands into the pseudocode even when no formal Reference was ever recorded. This is how the city-capture code was found (see priority item 5). Prefer this whole-range-dump-and-grep approach over `FindXrefs.java` for any string not already tied to a known address.

What came out of it:
    - **A rout mechanic (`FUN_00438fb0`), previously undocumented and load-bearing.** A unit is removed from the battle outright when its troops fall below its type's standard battalion size ÷ 25 (light inf 600 · heavy inf 240 · archers 140 · light cav 280 · heavy cav 100), when its morale drops to ≤ 19, or on a `Random(m)+Random(m) ≤ 29` check in 20…39 — and each rout costs every friendly unit 6 morale (dragging anyone under 30 out with it) while giving every enemy +5. Since both loss formulas cap at 40% of the losing side's *own* troops, this is the **only** way a unit ever reaches zero; every "wiped" unit in every battle this project has recorded was routed, not ground down. Two observed routs match the threshold exactly.
    - **The 40% loss cap confirmed on the attacker side** (`⌊0.4 × 7,135⌋ + 1 = 2,855`, observed exactly), closing item 4's remaining gap, plus five more exact defender-side hits.

[x] **The `ArmyRecord +6` `0xFFFF` anomaly, and the weekly moves formula with it.** One army record in the corpus (Ptolemaic army 9 at `(192, 96)`, Summer 270 week 7) reads `0xFFFF` in `moves` while `coveredCell` is a normal land code, so it is not the aboard-a-fleet marker. Settled from the code, two ways: the whole-application dump grepped for every symbol/pointer/word-index form that could write the field, and then all 71 functions referencing the army-table base `0x0047C1EC` disassembled and every `+6` write read by hand with its base register identified.
    - **The field is signed.** Every guard is `JLE`/`JGE` and every widening read is `MOVSX`, including the army panel's (`0x0043C3C6`), which prints the value straight — so the original would display `Moves --1`. `0xFFFF` means `−1`, and a `−1` army is frozen: it cannot even be *selected* (`0x004466EF`).
    - **Nothing writes `0xFFFF` deliberately.** All fourteen write sites are enumerated; thirteen write `0`, `1`, a floored decrement, or the weekly value. The `MOV word ptr [EBX],0xFFFF` at `0x00449F18` inside the creator `FUN_00449F08` — the obvious candidate — is the caller's **out-parameter for the new army index**, not the record. `FUN_00449F08` itself writes `0`, or `1` for an AI nation, at `0x00449F77`/`0x00449F91`, re-derived from the assembly and confirming `decompiled-unit-map-orders-and-record-fields.md` as written.
    - **Exactly one write has no floor:** `0x0044DBF7 SUB word ptr [EBX + 0x6],0x2`, the aboard-a-fleet branch of `FUN_0044DBA8`. Both AI entry points require `moves >= 1`, so a pre-value of `1` gives `−1` and *sticks* (the signed guard then skips the army). So the `0xFFFF` is an **underflow bug in the original**, not a sentinel — the "created this turn, maximum not yet computed" hypothesis is refuted, not merely unconfirmed. **Open:** the exact sequence that left this record with `−1` *and* a live map cell, since the only function restoring `+8` (`FUN_0044B840`, disembark) also zeroes moves. A record-pointer aliasing hazard around `FUN_0044ABE0`'s swap-remove is the leading candidate and is reported as a candidate.
    - **The weekly moves maximum, a standing open item in two reports:** `moves = 10 − min(5, floor(troops / 20000))`, minus `1` when supply is under 10 % — troop total only, composition irrelevant, floor 4. `FUN_0044A698` is **total troops**, not the "readiness" value `decompiled-turn-and-calendar-sequencing.md` called it. Checked on 627 army records in 54 saves: 625 satisfy `0 <= moves <= maximum`, the 2 exceptions being one army reinforced mid-week, which proves the maximum is **not** recomputed on a composition change.
    - Also corrected: `FUN_0045AF00` never reads `+6`; its filter is `FUN_0044AAB4` ("has not acted", i.e. `moves == recomputed maximum`) and it then warns on supply and *money*. That closes item 7's open "exact conditions in `FUN_0045AF00`". `FUN_0044AAB4`'s own low-supply test (`supplies * troops / 10000`) disagrees with the weekly tick's (`supplies * 10000 / troops`) — a real inconsistency in the original.

    See [army-moves-field-signed-and-the-ffff-underflow.md](reports/army-moves-field-signed-and-the-ffff-underflow.md), and the corrections in [decompiled-turn-and-calendar-sequencing.md](reports/decompiled-turn-and-calendar-sequencing.md), [decompiled-army-movement-and-river-cost.md](reports/decompiled-army-movement-and-river-cost.md) and [army-to-army-transfer-confirmed.md](reports/army-to-army-transfer-confirmed.md).

17. [x] **What raises a nation's mobilization percentage? Done — it is the recruitment *order*, not the mobilization.** `[confirmed]` in [decompiled-mobilization-and-mercenary-restock.md](reports/decompiled-mobilization-and-mercenary-restock.md) §5, from `TArmyRecruits_RecruitUnit` (`0x00454E78`), its symmetric counterpart `TArmyRecruits_DisbandUnits` (`0x004553B0`), and the identical inline arithmetic in the AI's `FUN_004504f4`:

    ```text
    order placed   : mobilized (+0x442) = min(100, mobilized + 1 + (troops × 1000) / wealth (+0x430))
    order cancelled: mobilized (+0x442) = max(0,   mobilized - 1 - (troops × 1000) / wealth)
    quarterly      : mobilized          = max(0,   mobilized - 3)
    initial        : mobilized          = 50
    ```

    Wealth is `Σ over the nation's cities (population × 3000)`, so the rate is the standing army as a fraction of the population. Mobilizing a completed slot does **not** touch the field. The alternative outcome this item allowed for — that nothing writes the field upward — is ruled out: three sites do. The observed spread (Rome 30, Gaul/Celtiberia/Galatia 97–100, four nations at 0) and [city-population-growth.md](reports/city-population-growth.md)'s 9 nation-quarters that departed from the `-3` decay are both explained by this rule. The reimplementation's T13 gap (build repo [#183](https://github.com/diegoami/imperial_conquest_2/issues/183)) can now be closed. *Original statement of the item follows.*

    The decay is settled and the cap is settled; the *increase* is missing entirely. [city-population-growth.md](reports/city-population-growth.md) confirms `FUN_00451b40`'s `−3` decays mobilization every quarter (floored at 0) and that the value reduces city supply production; [decompiled-recruitment-cost-formula.md](reports/decompiled-recruitment-cost-formula.md) confirms a hard 100% cap with its own literal, *"Your mobilisation rate is already 100%."* But **no per-order increment appears anywhere in the reports**, so a nation record field `+0x442` that starts non-zero, decays by 3 a quarter and is capped at 100 has no mechanism that ever raises it.

[x] **`FUN_0044b230` — the fortification and population loss a forced capture inflicts.** **Done 2026-09-23, at instruction level** (for build repo [#290](https://github.com/diegoami/imperial_conquest_2/issues/290)). The random-draw hypothesis below is superseded. See [decompiled-defection-and-siege-attrition.md](reports/decompiled-defection-and-siege-attrition.md#fun_0044b27c-instruction-by-instruction-2026-09-23). The original text follows. The *fact* is `[confirmed]` twice over: [decompiled-defection-and-siege-attrition.md](reports/decompiled-defection-and-siege-attrition.md) says forced capture (`FUN_0044bb18`) **always** changes fortification and population while defection (`FUN_0044bed8`) *"never writes to population or fortification anywhere"*, and [galatia-elimination-and-city-resupply-confirmed.md](reports/galatia-elimination-and-city-resupply-confirmed.md) confirms it city by city across all nine Galatian cities. **The formula is not.** The reimplementation's T17 therefore transfers a captured city without eroding either field, as a declared gap rather than an invented rule (build repo [#17](https://github.com/diegoami/imperial_conquest_2/issues/17)).

    **The two observed captures constrain it more tightly than the report states**, and this is worth writing down before anyone opens Ghidra:

    | City | Fortification | Population |
    | --- | --- | --- |
    | Laranda | 41 → 30 | 59 → 44 |
    | Gordium | 54 → 42 | 23 → 18 |

    Solving `floor(before × r) == after` for each field and intersecting the two windows per city:

    - **Laranda**: `r ∈ [0.7458, 0.7561)`
    - **Gordium**: `r ∈ [0.7826, 0.7963)`

    Two conclusions follow. **One multiplier explains both fields within each capture** — the windows intersect non-emptily for fortification and population separately, so the same factor is applied to both, which means a **single draw shared by the two fields**, not one per field. And **the two captures have disjoint windows**, so the factor is **not a constant**: it is drawn per capture. Both captures are in the same save transition, so this is not a per-turn or per-season value either.

    A shape consistent with both is `value = value × (75 + Random(10)) / 100`, one draw per capture (Laranda ≈ 0.75, Gordium ≈ 0.79, both inside their windows). **That is a hypothesis, not a finding** — many `(base + Random(span))/100` pairs fit two observations, and the constant could equally be a subtraction or a per-field table. It is recorded only so a decompilation pass knows what the answer has to look like.

    **What settles it**: decompile `FUN_0044b230`, read whether the draw is taken once and reused, and read the literal base and span. The windows above are then a free check — the right formula must be able to produce a value in `[0.7458, 0.7561)` and another in `[0.7826, 0.7963)`.

    **A cheap empirical alternative** if the decompilation stalls: any save pair spanning a forced capture gives another window. Three or four more captures would pin the base and span by intersection alone, without reading code. A run that takes several cities is the ideal source, so this is a good thing to watch for in the next play-through.

## Method, per target

1. Locate the form/procedure the same way prior reports did: Delphi RTTI method-name tables, the `TMainMenu`/form-adjacent streams, or a literal-string cross-reference (e.g. searching for dialog text like "quarterly", "Current tax", "New income") to find the owning code.
2. Decompile with a Ghidra headless script exporting C-like pseudocode for that function and its immediate callees to a text file.
3. Read the pseudocode and translate it to a plain-language rule, citing the function address(es) — same evidentiary standard as every existing report (`docs/reports/*.md`), which already cite save offsets and screenshot values this way.
4. Check the recovered formula against the empirical numbers listed above. State explicitly whether it matches, and if not, say so rather than adjusting the empirical reading to fit.
5. Write a new `docs/reports/*.md` and update `IC2.Data` doc comments / `docs/roadmap.md` only once a formula is actually confirmed this way — candidate/unconfirmed decompiled readings get the same "candidate" language already used throughout this project.
